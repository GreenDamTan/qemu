# IT8613E Super I/O 硬件监控设备维护记录

本文记录当前 QEMU 树中新增 `it8613e-superio` 设备的目标、使用方式、寄存器模型、Linux `it87` 驱动探测路径、运行时控制方式和维护注意事项。

这份文档面向后续维护者。目标不是完整复刻 ITE Super I/O 芯片的所有功能，而是提供一个独立、可维护、可通过命令行和 QMP 控制的 IT8613E 硬件监控外观设备，让 guest 能通过常见 `it87` 路径看到风扇、温度和电压传感器。

## 目标和边界

本次新增的目标：

- 新增一个独立 ISA 设备类型：

```text
it8613e-superio
```

- 不耦合 `adl-n` machine，也不在 q35 初始化路径中自动创建。
- 提供 IT8613E Super I/O 配置端口，默认地址为 `0x2e/0x2f`。
- 提供 IT87 风格 hardware monitor I/O 窗口，默认 base 为 `0x290`，实际 index/data 端口为 `0x295/0x296`。
- 让 Linux `it87` 驱动可以通过 Super I/O ID `0x8613` 识别为 IT8613E。
- 默认暴露 IT8613E 上常见的 `fan2`、`fan3`、`fan4`、`fan5`，并跳过 `fan1`。
- 支持命令行指定展示值，例如：

```sh
-device it8613e-superio,id=sio0,fan2=1000,temp1-mc=41000
```

- 支持运行时通过 QMP/monitor 修改传感器值，例如：

```text
qom-set /machine/peripheral/sio0 fan2 1800
qom-set /machine/peripheral/sio0 temp1-mc 45000
```

本次新增不保证：

- 完整实现 IT8613E 所有 Super I/O logical device。
- 完整复刻 datasheet 中所有 hardware monitor 寄存器。
- 提供真实的风扇控制闭环、温度曲线或 SmartGuardian 自动控制算法。
- 模拟 EC、ACPI、SMBus、GPIO、VID、蜂鸣器、watchdog 等其它 ITE 功能。
- 保证所有版本 Linux `it87` 驱动都按完全相同方式探测。当前实现主要按本仓库 `.cache/it87/it87.c` 的 IT8613E 路径对齐。

如果后续目标是完整芯片级复刻，需要收集真实机器上的 Super I/O dump、`sensors` 输出、`isadump`/`isadump -y` 结果、Linux `it87` dmesg、ACPI 资源声明和风扇控制行为，再逐步补齐。

## 实现文件

核心文件：

```text
hw/misc/it8613e.c
hw/misc/Kconfig
hw/misc/meson.build
```

构建入口：

```kconfig
config IT8613E
    bool
    default y if ISA_BUS
    depends on ISA_BUS
```

```meson
system_ss.add(when: 'CONFIG_IT8613E', if_true: files('it8613e.c'))
```

设备类型定义：

```c
#define TYPE_IT8613E_SUPERIO "it8613e-superio"
```

该设备继承：

```text
TYPE_ISA_DEVICE
```

因此它需要挂在 ISA bus 上。典型 x86/q35/pc machine 都有 ISA bus，可以直接通过 `-device` 手动创建。

## 为什么做成独立设备

IT8613E 是 Super I/O/hardware monitor 设备，不属于 Alder Lake-N PCIe root port 拓扑的一部分。

当前设计刻意保持独立：

- 不修改 `hw/i386/pc_q35.c` 来自动创建。
- 不依赖 `-machine adl-n`。
- 不占用 ADL-N 相关 PCI BDF。
- 不把传感器模型写进某个特定 machine。
- 只通过普通 QEMU 设备命令行启用。

这样后续可以在任意带 ISA bus 的 machine 中复用：

```sh
-machine q35 \
-device it8613e-superio,id=sio0
```

如果未来确实需要某个专用 machine 默认带 IT8613E，应在 machine 层单独增加自动创建逻辑，但不要把 IT8613E 设备本体和 machine 逻辑写在一起。

## 命令行使用

最小示例：

```sh
./build/qemu-system-x86_64.exe \
  -machine q35 \
  -m 2048 \
  -device it8613e-superio,id=sio0
```

指定风扇转速：

```sh
-device it8613e-superio,id=sio0,fan2=1000,fan3=1200,fan4=900,fan5=800
```

`fan2` 是短别名，等价于：

```sh
fan2-rpm=1000
```

完整一些的示例：

```sh
./build/qemu-system-x86_64.exe \
  -machine q35 \
  -m 2048 \
  -smp 4 \
  -device it8613e-superio,id=sio0,fan2=1000,fan3=1200,fan4=900,fan5=800,temp1-mc=41000,temp2-mc=43000,temp3-mc=39000,in0-mv=900,in1-mv=1000,in2-mv=1100
```

```text
0x290 + 5 = 0x295
0x290 + 6 = 0x296
```

## 运行时控制

设备属性允许 realized 后继续写入，因此可以通过 QMP 修改。

启动 QEMU 时建议给设备加 `id`：

```sh
-device it8613e-superio,id=sio0,fan2=1000
```

QOM 路径通常是：

```text
/machine/peripheral/sio0
```

读取当前值：

```json
{"execute":"qom-get","arguments":{"path":"/machine/peripheral/sio0","property":"fan2"}}
```

修改 fan2 转速：

```json
{"execute":"qom-set","arguments":{"path":"/machine/peripheral/sio0","property":"fan2","value":1800}}
```

修改温度：

```json
{"execute":"qom-set","arguments":{"path":"/machine/peripheral/sio0","property":"temp1-mc","value":45000}}
```

修改电压：

```json
{"execute":"qom-set","arguments":{"path":"/machine/peripheral/sio0","property":"in0-mv","value":950}}
```

如果使用 HMP monitor，可以写成：

```text
qom-get /machine/peripheral/sio0 fan2
qom-set /machine/peripheral/sio0 fan2 1800
qom-set /machine/peripheral/sio0 temp1-mc 45000
```

## 风扇 Lock 模式

如果希望某个风扇始终显示 QEMU 指定的固定值，可以打开 lock：

```sh
-device it8613e-superio,id=sio0,fan2=1000,fan2-lock=1
```

lock 语义：

- 被 lock 的风扇只使用 QEMU 侧指定的 RPM 值。
- guest 写 PWM 寄存器不会改变该风扇展示转速。
- guest 直接写 tach 高/低位寄存器也不会改变该风扇展示转速。
- QMP/HMP 仍可以通过 `fan2` 或 `fan2-rpm` 修改新的锁定值。

例如运行时修改 fan2 的锁定值：

```text
qom-set /machine/peripheral/sio0 fan2 1800
```

关闭 lock：

```text
qom-set /machine/peripheral/sio0 fan2-lock 0
```

重新打开 lock：

```text
qom-set /machine/peripheral/sio0 fan2-lock 1
```

lock 和 `fan*-mode` 的关系：

- `fan*-lock=1` 优先级最高。
- `fan*-lock=1` 时，即使 `fan*-mode=1`，guest 写 PWM 也不会按 PWM 重新计算 RPM。
- `fan*-lock=0` 且 `fan*-mode=1` 时，guest 写 PWM 才会按 `fan*-max-rpm * pwm / 255` 更新 RPM。
- `fan*-lock=0` 且 `fan*-mode=0` 时，RPM 主要由 QEMU 侧 `fan*` / `fan*-rpm` 属性指定。

## PWM 模式

默认 fan mode 是固定转速：

```text
fan2-mode=0
```

固定转速模式下：

- `fan2=1000` 或 `fan2-rpm=1000` 直接改 tach 寄存器。
- guest 写 PWM 寄存器不会改变展示转速。

PWM 模式：

```sh
-device it8613e-superio,id=sio0,fan2-mode=1,fan2-max-rpm=2400
```

PWM 模式下，guest 写对应 PWM duty 寄存器时，模型按下面关系更新展示 RPM：

```text
rpm = fan_max_rpm * pwm / 255
```

例如：

```text
fan2-max-rpm=2400
pwm=128
```

则 fan2 大约显示：

```text
1205 RPM
```

这只是一个简单线性模型，方便测试 guest 里的 fancontrol、pwmconfig 或手动 sysfs 写入。它不是 IT8613E 的真实风扇控制闭环。

## Super I/O 配置端口

默认配置端口：

```text
index  0x2e
data   0x2f
```

进入 ITE Super I/O 配置模式的序列：

```text
0x87, 0x01, 0x55, 0x55
```

如果 `sio-addr=0x4e`，进入序列最后一个字节为：

```text
0xaa
```

退出配置模式：

```text
index 0x02
data  0x02
```

关键全局寄存器：

```text
0x20/0x21  Device ID，返回 0x8613
0x22       Device revision，当前返回 0x01
0x07       Logical device number 选择寄存器
```

当前实现的 logical device：

```text
LDN 0x04   PME / Environment Controller，提供 HWM base
LDN 0x07   GPIO，提供 it87 判断 fan/pwm 通道所需的 pin 配置
```

PME LDN 中：

```text
0x30       active，固定返回 1
0x60/0x61  HWM base，默认返回 0x0290
```

这些寄存器在 guest 写入时保持只读语义。原因是 QEMU 的 I/O MemoryRegion 在 realize 时已经注册完成。如果允许 guest 修改 base，但不移动实际 I/O region，会造成 Super I/O config space 和实际端口不一致。

如果未来需要支持 guest 动态改 base，应实现 MemoryRegion 重新映射，而不是只改配置寄存器。

## HWM I/O 端口

默认 HWM base：

```text
0x290
```

当前 I/O region 覆盖：

```text
0x290 - 0x297
```

IT87 驱动实际使用：

```text
index  0x295
data   0x296
```

这对应代码中的：

```c
#define IT8613E_HWM_INDEX_OFFSET   5
#define IT8613E_HWM_DATA_OFFSET    6
```

访问方式：

```text
outb(reg, 0x295)
inb(0x296)
```

或者：

```text
outb(reg, 0x295)
outb(value, 0x296)
```

如果某个 guest 或固件代码按下面端口访问：

```c
outportb(0xA35, reg);
value = inportb(0xA36);
```

则 QEMU 设备需要把 HWM base 改成：

```sh
-device it8613e-superio,id=sio0,hwm-addr=0xa30
```

因为：

```text
0xa30 + 5 = 0xa35
0xa30 + 6 = 0xa36
```

## RPM 换算

Linux `it87` 和常见固件代码里的 16-bit fan tach 换算是：

```text
rpm = 1350000 / (raw * 2)
```

当前 QEMU 写寄存器时反向换算：

```c
raw = rpm == 0 ? 0xffff : clamp((1350000 + rpm) / (rpm * 2), 1, 0xfffe)
```

因此：

```text
fan2=1000
```

会写入 raw 约为：

```text
0x02a3
```

对应 fan2 tach 寄存器：

```text
0x19 = 0x02
0x0e = 0xa3
```

因此下面这种读取方式可以使用：

```c
outportb(0xA35, 0x19);
input_data1 = inportb(0xA36);

outportb(0xA35, 0x0E);
input_data2 = inportb(0xA36);

Divisor = (input_data1 << 8) | input_data2;
Speed = 1350000 / (Divisor * 2);
```

前提是 QEMU 设备使用：

```sh
-device it8613e-superio,id=sio0,hwm-addr=0xa30
```

如果使用默认 `hwm-addr=0x290`，则同样逻辑应访问：

```c
outportb(0x295, 0x19);
input_data1 = inportb(0x296);

outportb(0x295, 0x0E);
input_data2 = inportb(0x296);
```

如果 RPM 为 0，则写入：

```text
0xffff
```

Linux `it87` 会把它显示为 0 RPM。

温度：

```text
temp1  0x29

```

温度单位：

```text
temp*-mc = millicelsius
```

写入属性时会四舍五入到整摄氏度寄存器值。例如：

```text
temp1-mc=41000 -> 0x29 = 41
```

电压寄存器：

```text
in0   0x20
in1   0x21
in2   0x22
in3   0x23
in4   0x24
in5   0x25
in6   0x26
in7   0x27
in8   0x28
in9   0x2f
in10  0x2c
in11  0x2d
in12  0x2e
```

当前按 11 mV 分辨率换算：

```text
reg = mv / 11
```

实际代码中做了四舍五入和范围限制。

## Linux it87 驱动探测关系

本仓库参考文件：

```text
.cache/it87/it87.c
.cache/it87/Research/ITE_Register_map.csv
```

关键点：

- `DEVID 0x8613` 对应 `it8613` 类型。
- `it8613` features 包含五风扇、五 PWM、新温度映射和 11 mV ADC。
- 驱动会从 Super I/O LDN 0x04 读取 HWM base。
- 驱动会把 I/O resource 设置为 `base + 5` 到 `base + 6`。
- 驱动会读取 LDN 0x07 的 GPIO/PIN 寄存器判断 fan2 到 fan5 是否可用。

当前 GPIO 默认值意图：

```text
fan1/pwm1  隐藏
fan2/pwm2  保留
fan3/pwm3  保留
fan4/pwm4  保留
fan5/pwm5  保留
```

对应代码中设置：

```text
GPIO3  0x27 = BIT(1)
GPIO5  0x29 = 0
PINX1  0x2a = BIT(0)
BEEP   0xf6 = 0
```

这些值是为了通过 `it87.c` 的 IT8613E skip 逻辑，让 guest 中出现 fan2/fan3/fan4/fan5。

## 常见问题

### 设备类型无效

报错：

```text
'it8613e-superio' is not a valid device model name
```

原因通常是当前运行的 exe 没有编进新设备。

检查：

```sh
grep it8613e build/build.ninja
strings ./build/qemu-system-x86_64.exe | grep it8613e
./build/qemu-system-x86_64.exe -device help | grep it8613e
```

没有输出就重新生成并编译：

```sh
cd /d/git/GreenDamTan/qemu/build
./pyvenv/bin/meson.exe setup --reconfigure . ..
ninja qemu-system-x86_64.exe
```

### guest 没有出现 hwmon

先确认设备已加入 QEMU 命令行：

```sh
-device it8613e-superio,id=sio0
```

再在 guest 中检查：

```sh
dmesg | grep -i it87
ls /sys/class/hwmon/
```

如果驱动没有自动加载：

```sh
modprobe it87
```

如果 guest 内核没有启用 `CONFIG_SENSORS_IT87`，需要换内核、加载模块，或把驱动编进去。

### fan2 写了但 sensors 不变

如果通过 QMP 修改：

```text
qom-set /machine/peripheral/sio0 fan2 1800
```

但 guest `sensors` 暂时不变，可能是 `it87` 驱动缓存还没刷新。稍等几秒或直接读 sysfs：

```sh
cat /sys/class/hwmon/hwmonX/fan2_input
```

也要确认 QMP 路径正确。设备 ID 是 `sio0` 时通常是：

```text
/machine/peripheral/sio0
```

### guest 改 PWM 但 fan2 不变

如果启动或运行时设置了：

```text
fan2-lock=1
```

这是预期行为。lock 开启后，guest 写 PWM 或 tach 寄存器都不会改变 fan2 展示值。

如果希望 guest PWM 生效，需要：

```text
qom-set /machine/peripheral/sio0 fan2-lock 0
qom-set /machine/peripheral/sio0 fan2-mode 1
```

### hwm-addr 改了以后 guest 找不到

`hwm-addr` 必须 8 字节对齐：

```text
0x290
0x298
0x2a0
```

不能使用：

```text
0x295
```

因为 `0x295` 是 index port，不是 HWM base。

如果写：

```sh
-device it8613e-superio,hwm-addr=0x298
```

guest 驱动实际访问：

```text
0x29d/0x29e
```

### sio-addr 选择

默认：

```text
0x2e/0x2f
```

也可以改为：

```sh
-device it8613e-superio,sio-addr=0x4e
```

这种情况下进入 Super I/O 配置模式的最后一个字节是 `0xaa`，这与 ITE 常见规则一致。

### guest 写 Super I/O base 不生效

当前模型有意让 LDN 0x04 的 active 和 base 寄存器保持只读语义。

原因是 QEMU I/O region 在设备 realize 时注册。如果 guest 改了 Super I/O config 中的 base，但 QEMU 没有移动 MemoryRegion，会出现配置显示和实际端口不一致。

需要动态 base 时，后续应实现 unregister/register 或 MemoryRegion alias 重映射。

## 后续扩展方向

可以继续做的方向：

- 增加 fan label 或 board-specific 默认值文档。
- 根据真实 IT8613E dump 校准默认寄存器值。
- 增加更多温度通道或 VIN 通道的真实启用逻辑。
- 把 `fan*-mode` 从数字属性改成 enum/string 属性，例如 `fixed`、`pwm`。
- 实现更接近 `it87` 的 PWM enable、manual/auto 模式寄存器语义。
- 支持 guest 动态改 HWM base 并同步移动 I/O region。
- 增加 qtest 单元测试，固定验证 `DEVID=0x8613`、HWM offset、fan tach 换算和 QOM 属性。

不建议短期做的方向：

- 把设备直接塞进 ADL-N machine。
- 为了让 `sensors` 输出更像某块主板而硬编码大量 board-specific label。
- 在没有真实寄存器 dump 的情况下大规模补未知寄存器默认值。

当前更稳妥的维护方式是：先保持 `it8613e-superio` 作为可手动添加、可运行时控制的独立设备，再按 guest 驱动实际需求逐步扩展。
